# ADR 002: Implementing QBFT Consensus and Dual-Trigger Merkle Tree Batching for Degree Issuance

## Status
**Approved**

## Context
In the degree verification system, Higher Education Institutions (CSDT) need to issue diplomas either individually or in bulk (e.g., during graduation seasons with thousands of graduates). Interacting directly with the blockchain network for each individual degree issuance introduces several architectural challenges:

1. **UI/UX Bottleneck**: Sending synchronous blockchain transactions via Web API causes high request latency, leading to a poor user experience and potential connection timeouts during bulk imports.
2. **Validator Node Overload**: High-frequency, individual transaction bursts can easily saturate the transaction pool (Mempool) of Hyperledger Besu Validator nodes, degrading network performance.
3. **Storage Inefficiency**: Storing each degree data hash as an isolated blockchain transaction results in rapid ledger size growth and excessive disk I/O, consuming unnecessary system resources.
4. **Empty Block Resource Waste**: Standard blockchain configurations produce empty blocks at fixed time intervals even when no transactions exist, causing dead weight on ledger storage.

## Decision
To maximize throughput, minimize storage footprint, and ensure an optimal user experience, we decide to establish the following architectural blueprint:

### 1. Blockchain Layer: Adopting QBFT Consensus with Delayed Empty Blocks
* Implement the **QBFT (Quorum Byzantine Fault Tolerance)** consensus mechanism on the private Hyperledger Besu network. QBFT is chosen over IBFT 2.0 as it represents the enterprise-grade, deterministic, and most robust consensus algorithm optimized for Besu.
* Configure `mining-empty-blocks = false` within the genesis configuration. This stops validators from generating wasteful empty blocks when the network is idle, preserving host disk capacity.

### 2. Application Layer: Decoupled Buffer (Application Mempool)
* Web API requests will no longer trigger immediate blockchain transactions.
* When a university registrar imports degrees, the Web API performs fast data validation, persists records into the relational database with a `Pending_Confirmation` state, pushes the unique identifiers (IDs) into a high-throughput Message Queue (or Database-backed queue), and immediately returns a success status to the client.

### 3. Processing Layer: Dual-Trigger Hosted Service (.NET Background Worker)
* Develop a native .NET `BackgroundService` that continuously monitors the queue and manages batch boundaries using a **Dual-Trigger** strategy:
    * **Trigger 1 (Max Batch Size)**: The queue accumulates a threshold of **500 degrees**.
    * **Trigger 2 (Max Wait Time)**: A maximum timeout of **3 minutes** (or 5 minutes) lapses since the oldest message entered the current batch, regardless of the threshold.

### 4. Cryptographic Layer: Merkle Tree Batch Anchor
* Upon either trigger condition being met, the Worker pops the batch and constructs a local **Merkle Tree** out of the 500 degree data hashes (`data_hash_local`).
* Instead of emitting 500 network calls, the worker uses **Nethereum** to broadcast exactly **one single transaction** containing the computed **Merkle Root** to the Smart Contract. 
* Once the transaction receipt is confirmed via QBFT block finality, the background worker bulk-updates the local database states to `Confirmed`.

## Consequences

### Advantages
* **Asynchronous UI/UX (Non-blocking)**: Registrars do not experience UI lag. Bulk imports finish instantaneously on the frontend with a "Processing in background, expected completion within 3 minutes" status notification.
* **Drastic Ledger Size Reduction**: Storing a single Merkle Root instead of 500 individual hashes minimizes blockchain storage growth by a factor of 500x.
* **Validator Traffic Smoothing**: Mempools of private Hyperledger Besu validator nodes remain highly stable. High peak loads during graduation seasons are absorbed elegantly at the application queuing tier.
* **Seamless US-3 Verification**: The verification engine (**US-3**) remains fully robust. To verify a degree, the system retrieves the raw `plain_data_json`, recomputes the leaf hash, utilizes the stored Merkle Proof paths, and validates it against the immutable Merkle Root anchored on-chain.

### Disadvantages & Challenges
* **Eventual Consistency Delay**: Degree verifications have a tiny latency gap (up to 3-5 minutes) between application submission and absolute blockchain confirmation.
* **Proof Path Management**: The application layer must maintain a mechanism to regenerate or store Merkle Proofs for individual leaf verifications.
* **State Alignment**: If a batch transaction fails on the blockchain due to contract errors, the worker must handle transactional rollbacks or route failed batches to a Dead Letter Queue (DLQ) for self-healing/retries.
