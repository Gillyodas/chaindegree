# ADR 002: Using Smart Contract Mapping Instead of Event Logs for State Verification

## Status
**Approved**

## Context

The ChainDegree system anchors Merkle Roots on a private Hyperledger Besu blockchain.

After submitting an anchor transaction, the backend worker must determine whether a specific batch has already been successfully anchored in order to:

1. Prevent duplicate blockchain transactions (Idempotency).
2. Recover correctly after worker crashes or database failures.
3. Verify blockchain state during startup or retry workflows.
4. Keep the verification logic simple and deterministic.

Two possible approaches exist:

- Query Smart Contract Events (`BatchAnchored`)
- Query Smart Contract Storage (`mapping(bytes32 => BatchMetadata)`)

Although event logs provide historical information, they are not part of the contract state and require log filtering/indexing.

## Decision

The application will use the Smart Contract `mapping(bytes32 => BatchMetadata)` as the primary source of truth.

```solidity
mapping(bytes32 => BatchMetadata) public batches;
```

The backend verifies blockchain state by calling:

```solidity
batches(batchId)
```

instead of scanning or decoding emitted events.

The `BatchAnchored` event remains available only for operational purposes such as blockchain explorers, debugging, monitoring, or external integrations.

Business logic will never depend on event logs.

## Consequences

### Advantages

* **Deterministic state lookup**

  Every `batchId` maps directly to exactly one blockchain state.

* **Simple Idempotency**

  During retry or recovery:

  ```
  if batches(batchId).Exists == true
      -> already anchored
  else
      -> send transaction
  ```

* **Crash Recovery**

  Even if:

  ```
  Blockchain Success
  Database Update Failed
  Worker Restart
  ```

  the worker can recover by querying contract storage.

* **Less Infrastructure**

  No event indexing.

  No event replay.

  No log cursor management.

  No event synchronization service.

* **DDD Friendly**

  The backend reasons about business state instead of blockchain history.

### Disadvantages

* Events can be queried faster for analytics over large historical ranges.

* Historical event streams are still useful for:

  - Monitoring
  - Blockchain Explorer
  - Audit visualization

  but not for business decisions.

## Rationale

The backend cares about the current existence of a batch rather than the historical sequence of blockchain events.

Using contract storage provides a simpler, safer, and more deterministic architecture while significantly reducing recovery complexity.
