# ADR 004: Using LocalEnvSigner During Initial Development

## Status

**Approved**

## Context

Blockchain transactions require a private key for digital signing.

Several signer strategies are available:

- Private Key stored in `.env`
- Azure Key Vault
- HashiCorp Vault
- Remote Signer
- Hardware Security Module (HSM)

Enterprise-grade key management solutions provide stronger security but introduce significant infrastructure complexity.

The current phase focuses on validating blockchain integration rather than production deployment.

## Decision

The project will implement `LocalEnvSigner` during development.

`LocalEnvSigner` wraps Nethereum's `Account` abstraction and loads the private key from application configuration.

A signer abstraction (`IBlockchainSigner`) is introduced from the beginning so that future migration requires only replacing the implementation.

```
Application

↓

IBlockchainSigner

↓

LocalEnvSigner

↓

Nethereum Account
```

Future implementations may include:

```
KMSSigner

VaultSigner

RemoteSigner

HSMSigner
```

without changing application logic.

## Consequences

### Advantages

* **Fast Development**

No cloud infrastructure is required.

Developers can clone the repository and start immediately.

---

* **Minimal Complexity**

Only one signer implementation is maintained during early development.

---

* **Architecture Remains Extensible**

The Dependency Inversion Principle is preserved.

Replacing the signer does not affect:

- Worker
- Application Services
- Domain Logic

---

* **Suitable for Local Development**

The risk of local development keys is acceptable because they contain no production assets.

### Disadvantages

* Private keys exist on the application host.

* Anyone with machine access may obtain the signing key.

* Key rotation must be performed manually.

* Not suitable for production environments.

## Future Migration Path

When production deployment is required:

```
LocalEnvSigner

↓

KMSSigner
or

RemoteSigner

↓

Cloud Production
```

No business logic changes are expected because the application depends only on `IBlockchainSigner`.

## Rationale

The project prioritizes correctness, architecture, and maintainability over enterprise infrastructure.

`LocalEnvSigner` provides the simplest implementation while preserving a clean migration path toward secure key management solutions.
